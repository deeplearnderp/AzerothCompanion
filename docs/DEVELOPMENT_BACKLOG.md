# Azeroth Companion Development Backlog

This document tracks the long-term evolution of Azeroth Companion.

Its purpose is to record:

- Technical debt
- Architecture improvements
- Deferred features
- Blizzard API verification
- UX improvements
- Future modules
- Ideas discovered during development

This document is intentionally version-controlled.

Completed items should be checked off rather than deleted whenever practical.

### v1.0 Visual Polish Sprint

A full visual/UX audit of every Dashboard file (`Layout.lua`, `Format.lua`, `DashboardCard.lua`, `BaseWindow.lua`, `BaseWidget.lua`, `Home.lua`, `Sections.lua`, `Rows.lua`, `Navigation.lua`, `Pages/Achievements.lua`) before any implementation, per the sprint's own "audit first" brief -- no new gameplay systems, only presentation.

**Critical bug found and fixed:** Home.lua built its page as a plain `Frame` with no `ScrollFrame`, unlike every other page (`CreateDataPage`). Stacking all 12 Home cards at their real heights runs to roughly 1,600px of content in a ~670px usable viewport -- WoW does not clip a plain Frame's children to its own bounds, so the bottom several cards (Recent Activity onward, plus the version footer) rendered past the window's edge, unclipped and completely unreachable. Fixed by giving Home the exact same ScrollFrame/ScrollChild shape every other page already uses, with content height measured after the fact (from the greeting to the footer) since every Home card's height is dynamic, unlike a static-schema page's.

**Biggest visual-quality gap found and fixed:** zero window or card in the entire addon had any border/edge treatment -- `BaseWindow.lua`, `DashboardCard.lua`, and even `SettingsWindow.lua`'s two backdrop panels all rendered as flat, edgeless `SetColorTexture`/`bgFile`-only rectangles. This was the single biggest reason the addon read as an unfinished placeholder rather than a real UI. All four now use a real `BackdropTemplate` bordered backdrop (`Interface\Tooltips\UI-Tooltip-Border`, a thin Blizzard edge texture chosen to keep this addon's flat, modern look rather than an ornate parchment frame).

**Icons wired in, using only data already collected:** `AchievementsModule.lua` already captured each achievement's real Blizzard icon FileID and never rendered it anywhere; `CharacterModule.lua` already captured `classFile` (the non-localized class token) and never rendered a class icon. New `DashboardCard:SetIcon(texture)`/`SetClassIcon(classFile)` (the latter using the same `CLASS_ICON_TCOORDS` atlas technique the default UI's own group/raid frames use, confirmed via a real published addon's source before use) -- wired to Home's Achievements card (recent achievement's real icon) and Profile card (class icon). Purely additive to `DashboardCard`: a card that never calls either method is laid out exactly as before.

**Chart added, using only data already collected:** new `Dashboard:LayoutRunLevelChart` (`Rows.lua`) -- a small bar-timeline of recent Mythic+ runs (oldest to newest, bar height = key level, color = timed/failed), rendered on the MythicPlus page just below the Hero section, directly above the existing Recent Runs table it visualizes. Purely a different rendering of `GetRecentRuns()`'s already-recorded data -- computes nothing new.

**Animation added:** `DashboardCard:SetBarValue` now eases toward its new value over 0.35s (ease-out) instead of snapping, via a per-bar `OnUpdate` that clears itself the instant the animation finishes -- an idle card costs nothing between refreshes, and a repeated refresh with an unchanged value never restarts it.

**Also fixed while auditing:** the `.toc`'s `## Notes:` field -- the line every player sees in the in-game AddOns list -- was the placeholder text `"Framework"`, left over from before this addon had a name worth describing. Replaced with a real one-line description of what the addon does. Added `## IconTexture`, previously unset (reusing the same book icon already used for the minimap launcher, not a new asset).

**Audited and found already in good shape, not changed:** empty-state messaging (`ShowEmptyLine`, "Caught Up" wording) and hover feedback on every already-clickable element were already consistent and complete; not every priority in the sprint's brief needed a code change to satisfy.

Triggered by live reports of runtime errors while hovering NPCs and interacting with Blizzard UI inside Mythic+ dungeons (e.g. Algeth'ar Academy), and research confirming other retail addons (TooltipInfo, TooltipExtraData, Rarity, Quester) hit the same class of failure after Blizzard tightened Secret Value / `TooltipDataProcessor` restrictions. - [x] **Complete callback inventory -- exactly two secure-callback surfaces exist in the whole codebase.** Repo-wide grep for `TooltipDataProcessor`/`Menu.ModifyMenu`/`HookScript`/`SetScript`/`securecallfunction`/`GameTooltip`/every `Unit*` API/`Gossip`/`Merchant`/`Inspect`/`ContextData`, every hit read in full context. Confirmed: exactly one `TooltipDataProcessor.AddTooltipPostCall` registration (`PlayerJournalTooltip.lua`) and exactly one `Menu.ModifyMenu` registration site (`PlayerJournalContextMenu.lua`, looped over 9 player/party/raid/friend/guild tags) exist anywhere in this addon's own code -- no Gossip/Merchant/Inspect/`UnitPopup` hook exists at all, and the only two `HookScript` calls in the whole tree are inside the third-party `LibDBIcon-1.0` library (Minimap tooltip), unrelated to unit identity. Every other `Unit*`/`GUID` call in the codebase (`CharacterModule`, `MythicPlusModule`'s combat-log interrupt tracking, `PlayerJournalModule`'s roster tracking, `DatabaseService`, `ErrorCapture`) operates on a literal, addon-chosen unit token (`"player"`, `"party1"`, ...) from an ordinary `RegisterEvent` handler -- never a value obtained from inside Blizzard's secure callback dispatch, so none of it is reachable by the Secret Value restriction regardless of which API is called. This is the key distinction the whole audit turns on: secrecy is injected by *how* a value reached a callback, not by *which* `Unit*` API is later called on it.
- [x] **Confirmed unsafe: none currently open.** The two patterns previously confirmed broken by real in-game errors (`tooltip:GetUnit()`'s return value; the postcall's own `data.guid` field) were already removed in an earlier pass, replaced by the `KnownUnits` cache architecture. Confirmed via grep that neither pattern exists anywhere in the codebase today.
- [x] **Suspicious, both hardened this pass (still `NEEDS_LIVE` pending a human's confirmation, no longer an open crash risk):**
  - `pj.tooltipLineTextSafe` (`data.lines[1].leftText`, read inside the tooltip postcall) -- elevated priority: this postcall fires for every unit tooltip, players and NPCs alike, so it is exercised far more heavily in NPC-dense content like Mythic+ dungeons than in open-world play, consistent with the reported symptom.
  - `ctxmenu.contextDataUnitSecretValue` (`contextData.unit`, read inside the `Menu.ModifyMenu` callback) -- structurally identical to the two already-confirmed-broken tooltip patterns, for a different Blizzard callback family.
- [x] **New shared helper: `AC.SecretValueGuard:TryRead(context, fn, ...)`.** New file `Core/Security/SecretValueGuard.lua` (no lifecycle, same shape as `Core/Presentation/Presentation.lua`), added to the `.toc` right after `Presentation.lua`. `pcall`-wraps a read of Blizzard secure-callback data, forwards every return value on success (table-packed, so it's correct for a one-value or two-value read without the caller special-casing arity), returns nothing and Debug-logs the caught error under a short `context` label on failure. Applied to the two suspicious reads above (`PlayerJournalTooltip.lua`'s `data.lines[1].leftText`, `PlayerJournalContextMenu.lua`'s `contextData` read covering both the `unit` path and the `name`/`server` fallback in one call) -- both now degrade to silently skipping that one tooltip/menu-entry instead of throwing a visible Lua error. Deliberately **not** applied to any ordinary-event-handler `Unit*` call in the inventory (they were never at risk, and wrapping safe code in pcall would just be noise) -- this is a defensive boundary at the edge of code this addon does not control (Blizzard's own undocumented, per-patch secrecy policy, already wrong-footed twice under this exact feature), not a nil-guard hiding this addon's own bug, which is the category the framework-stabilization pass explicitly rejected. `VerificationService.lua`'s two affected registry entries updated to describe the new graceful-degradation behavior.
- [x] **Files requiring changes: 4.** New: `Core/Security/SecretValueGuard.lua`, `AzerothCompanion.toc`. Changed: `Core/UI/PlayerJournalTooltip.lua`, `Core/UI/PlayerJournalContextMenu.lua`, `Core/Services/VerificationService.lua`.

## Secret Value Diagnostics Hardening Pass (2026-07-14)

Framework reliability and diagnostics pass, not a gameplay feature -- hardens `SecretValueGuard` into a self-diagnosing subsystem and makes it a first-class Developer Runtime capability, so a future Blizzard secret-value policy change is visible in the Developer Panel instead of requiring another live-error-driven investigation. See `docs/GameplayModuleArchitecture.md`'s "Secret Value Diagnostics Hardening Pass" subsection for the full writeup.

- [x] **`SecretValueGuard:TryRead` redesigned to return structured diagnostics.** New contract: `ok, value, result = TryRead(context, fn, ...)`. `result` carries `status` (`SUCCESS`/`SECRET_VALUE_BLOCKED`/`CALLBACK_EXCEPTION`/`UNKNOWN_EXCEPTION`), `context`, `source` (auto-derived from `context`'s dotted prefix, e.g. `"tooltip"` from `"tooltip.lineText"`), `message`, `stack`, `timestamp`. `fn` now returns exactly one value (wrap multiple fields in a table) instead of the first draft's full `pcall`-return-list forwarding -- simpler, predictable arity at every call site. Callers that don't care about diagnostics are unaffected: `local ok, value = TryRead(...)` reads exactly as simply as before.
- [x] **Real bugs still fail normally -- enforced in code, not just documented.** `TryRead` classifies every failure via a centralized `IsSecretValueError(message)` heuristic (checks for "secret" in the error text -- both real errors this addon has hit contain it). A genuine secret-value failure is absorbed silently (the guard's whole purpose). Anything else (`CALLBACK_EXCEPTION`/`UNKNOWN_EXCEPTION` -- a real bug in the wrapped code) is recorded for diagnostic context and then **re-thrown** (`error(valueOrError, 0)`), propagating to the normal error pipeline exactly as if the guard weren't there. This directly satisfies the explicit requirement that framework bugs must still fail normally so they can be found and fixed -- `SecretValueGuard` isolates the Blizzard boundary, it does not become a second, quieter way to hide this addon's own mistakes.
- [x] **New Developer Runtime capability: `SecretValueEvents`.** New file `Core/Runtime/SecretValueEvents.lua`, the second capability after `ErrorCapture` (added to the `.toc` right after it). Same shape by design: aggregated by `context|status` key (a recurring event coalesces into one entry with a growing `occurrenceCount`, never log/entry spam), capped at 200 unique entries with FIFO eviction, notifies via `AC.DeveloperRuntime:NotifyUpdate` (combat-aware, matching `ErrorCapture`). Recording is gated on Developer Mode (`Install()`/`Remove()` toggle `Enabled`) -- `SecretValueGuard`'s actual `pcall` protection is never gated, every player is protected from a crash at these boundaries regardless of Developer Mode; only whether an event gets *recorded* for the Panel is gated, the same trade-off `ErrorCapture` already makes.
- [x] **Structured logging.** `SecretValueEvents:Record` now Debug-logs a labeled, multi-line block (`[SecretValueGuard]` / `Context:` / `Status:` / `Reason:` / `Occurrences:`) with the entry's live running occurrence count, replacing the prior single generic "Secret-value read blocked" sentence.
- [x] **New "Secret Values" tab in the Developer Panel, reusing the Errors tab's infrastructure rather than duplicating it.** Same `AC.Dashboard:LayoutAccordionRows` engine and detail-field primitives; three previously Error-tab-only local helpers (`TruncateErrorMessage`/`AddErrorDetailHeader`/`HideErrorDetailHeader`, already fully generic in logic, just narrowly named) were renamed to `TruncateMessage`/`AddDetailHeader`/`HideDetailHeader` and are now called directly by both tabs -- no second copy of any of it. Copy JSON/Copy Text/Copy Summary needed zero new code (both tabs populate the same generic `self.CurrentTabData`/`self.CurrentTabSummaryLines` the shared footer already reads). Collapsed rows show Context+Status (colored -- `critical` for a real re-thrown bug, `dim` for the expected secret-value-blocked case)/Message preview/Occurrences+Last Seen, matching the requested column set as the same stacked-line shape every other log-style tab in this file already uses. Clear Events button mirrors Clear Errors exactly.
- [x] **Verification, per this pass's own request:**
  1. Every place `SecretValueGuard` is used today: exactly two -- `PlayerJournalTooltip.lua` (`context = "tooltip.lineText"`) and `PlayerJournalContextMenu.lua` (`context = "ctxmenu.contextData"`).
  2. Every place it should eventually be used: nowhere else today (confirmed via the prior pass's full callback inventory) -- but any future `TooltipDataProcessor`/`Menu.ModifyMenu`/Gossip/Merchant/Inspect hook should wrap its own secure-callback reads in `TryRead` from day one, gaining aggregation/logging/Panel visibility with zero new plumbing.
  3. Remaining Blizzard callback boundaries worth monitoring: none currently hooked beyond the two above.
  4. Assumptions still requiring live verification: unchanged -- `pj.tooltipLineTextSafe` and `ctxmenu.contextDataUnitSecretValue` are both still `NEEDS_LIVE`, but are now self-reporting via the Secret Values tab instead of requiring a reproduced crash.

**Remaining known issues / deferred work (not addressed this pass, tracked deliberately):**
- Same two `NEEDS_LIVE` items as the prior pass -- now watchable directly via `/ac dev` -> Secret Values tab instead of only Debug logging.
- `IsSecretValueError`'s "contains the word 'secret'" heuristic is a best-effort classifier, not a Blizzard-documented contract -- if a future secret-value error ever uses different wording, it would misclassify as `CALLBACK_EXCEPTION`/`UNKNOWN_EXCEPTION` (re-thrown, visible in Errors tab) rather than being silently absorbed. Treated as an acceptable, easily-diagnosed failure mode (the Errors tab would show it plainly) rather than a reason to guess at additional wording patterns with no second real example to confirm them against.

## Accordion Polish Pass

After using the Accomplishments/Journey accordion pages in-game, a real layout bug and three UX gaps were found and fixed at the shared engine level (`Core/UI/Dashboard/Sections.lua`/`Rows.lua`), not with per-page padding hacks -- every fix automatically benefits Accomplishments, Journey, MythicPlus's Recent Runs table, and any future accordion page. Full detail in `docs/GameplayModuleArchitecture.md` section 1.3's "Accordion Polish Pass" subsection.

- [x] **Real bug fixed -- root cause of section headers occasionally clipping the following section:** `Dashboard:BeginSection`/`Dashboard:AddDivider` created a brand-new, never-pooled FontString/Texture on every call. Every dynamic page's `Layout_` re-runs this on every refresh -- on accordion pages, on every single row click -- so old ghost headers/dividers from earlier layout passes never got hidden, froze at stale Y positions, and could visually intrude into a section that had since become shorter. - [ ] `SetTooltip`/`SetEnabled` are reimplemented near-identically across all 7 `BaseWidget`-derived widgets (Button/Checkbox/ColorPicker/Dropdown/EditBox/Label/Slider) instead of being hoisted onto `BaseWidget` itself. Unrelated to the Dashboard split; a future Widgets cleanup pass.
- [x] Consolidate the priority-to-stars star string, previously written inline in two places -- `Rows.lua:LayoutItemRows` (via `DashboardFormat.PriorityToStars`) and `DashboardCard:SetStarRating` (its own undocumented duplicate of the same `math.ceil(priority/20)` formula, never actually routed through `PriorityToStars`). - [ ] `ModuleManager:InitializeModules/EnableModules/DisableModules/ShutdownModules` (`Core/Managers/ModuleManager.lua`) call each registered module's lifecycle method with no `pcall`. Found during the Developer Panel registration audit -- not a proven cause of any observed bug, but a real single point of failure: if any one module's `Initialize()`/`Enable()` throws, every module registered after it in `ModuleManager.Order` silently never runs its own lifecycle call, with no visible error to a player running with Lua errors off (Blizzard's default). Flagged as future hardening, deliberately not implemented alongside the single-command Developer Mode fix above (out of scope for that pass).
